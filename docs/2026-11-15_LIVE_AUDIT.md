## 4. 直接编码原始字典也存在缺项

以下检验只修改内存副本，没有向游戏发送相应动作，也没有改写原始记录。

- 手牌槽位：第 11 帧交换 `Defend_G` 与 `Survivor`，完整 2945 维向量不变；第 20 帧交换 `Masterful Stab` 与 `Finisher` 也不变。
- 原因是手牌区块保存整体卡牌计数及各槽位费用、类型等属性，没有完整绑定槽位与 card ID；按槽位出牌的策略因此可能分不清目标。
- 奖励选牌：第 34 帧同时反转 `screen_state.cards` 与 `choice_list`，向量不变；改变第一项 card ID、名称及选项名称，向量也不变。
- 敌方状态：删除多层护甲时 30/30 检验不改变向量；删除虚弱时 17/17 不改变向量。当前攻击伤害已受虚弱影响，但持续层数没有因此被保留。
- 中毒和易伤的删除会改变向量，因此不能概括成“所有敌方 powers 都没编码”。
- 遗物：改变苦无 counter 不改变向量；遗物是否持有与遗物当前计数需要分别表达。
- 攻击：保持总伤害不变、改变单次伤害及攻击次数，向量不变；两者对多次攻击、防御效果的意义可能不同。
- 意图表：另对旧日志检查发现 `ATTACK_DEFEND` 未列入 13 项映射；GameState 的枚举还比该映射更少。

主要位置：`src/training/encoder.py` 的手牌、怪物、遗物和全局区块，以及 `configs/encoder_ids.yaml`。
继续增加向量维数或网络层数，不能自动补回这些缺失语义。

原始接口也有覆盖边界：本次卡牌字典没有直接给出动态伤害、格挡和效果数值；战斗字典也没有终结技所需的本回合攻击出牌数。
这些信息需由可靠规则、动作历史或扩展接口补齐。策略输入应保留决策所需的可观察信息及必要历史，不能把未来抽牌顺序当作已知信息。

## 5. RL 环境与真实状态之间仍未接通

`src/env/sts_env.py` 的 `_encode_observation` 在没有 combat_state 时直接返回全零向量。
离线装载真实第 33、34 帧后，RL 观察仍为 2945 维，但非零元素均为 0；奖励和选牌信息无法进入该观察。

动作掩码也未覆盖全部可用命令：

- 第 12 帧为 `HAND_SELECT`，Mod 允许 `confirm`，环境合法动作中没有确认动作 172。
- 第 34 帧允许 `skip`，环境只给出三个 choose 动作，没有跳过动作 177。
- 掩码需要按真实界面语义验收，不能只检查数组长度或是否至少有一个合法值。

奖励问题通过真实状态离线回放复现，方法为公开 `set_state` 接口加现有奖励计算：

- 第 16 → 17 帧，玩家实际损失 3 点生命，计算奖励为 0。
- 第 32 → 33 帧，战斗完成并进入奖励界面，计算奖励为 0，terminal 为 true。
- `set_state` 会覆盖用于差分的生命基线；战斗结束后缺少 combat_state，奖励函数又直接返回 0。
- 这证明该回放调用方式存在问题，不等于已跑过完整在线 RL 训练，或证明所有调用方式都产生零奖励。

`reset` 目前清空状态；`step` 不发送 Mod 命令、不等待真实后继状态，动作执行仍留给外部处理。
单战斗终止、整局终止及时间截断也需要分别定义。现有代码不构成完整的真机 RL 环境。

## 6. 动作协议与训练入口

CommunicationMod 1.2.1 的出牌槽位为 1-based，敌人目标、药水槽位、choose 选项均为 0-based。
例如第一张牌攻击第一只怪是 `play 1 0`；第一槽药水攻击第一只怪是 `potion use 0 0`。
本地 `src/core/action.py` 的药水输出错误地将槽位加 1，反向解析又减 1；本次独立控制通道使用了正确协议。
协议依据为官方 [v1.2.1 CommandExecutor.java](https://github.com/ForgottenArbiter/CommunicationMod/blob/v1.2.1/src/main/java/communicationmod/CommandExecutor.java)。

本地标准动作空间为 179，结束回合 ID 为 170；旧预处理支路声明 250，结束回合 ID 为 100，两套语义不能混用。
`src/agents/rl_agent.py` 的 sklearn warm start 仍为占位；PyTorch 分支未完成实际权重复制，完成日志不能作为验收证据。
本地 Agent 包还会连带导入 LLM 模块；`state_compressor.py` 第 149 行的 `//` 注释触发 Python 语法错误。

## 8. 建议修复次序与验收门槛

1. 固定开发基准：记录远程提交与本地差异，确认现行 encoder/action 版本；验收是同一入口、同一 schema，不再用不同副本结果互相替代。
2. 保留状态：修复 GameState 往返及非战斗观察；验收是上述真实帧的意图、伤害次数、powers、回合、牌堆、遗物和奖励字段均按定义保留。
3. 修复编码语义：绑定手牌槽位与身份，表示奖励候选、遗物计数及必要敌方状态；验收是影响决策的受控变化会产生预期编码差异。
4. 统一动作与掩码：修复药水索引及 confirm/skip，淘汰混用编号；验收是各已覆盖界面的合法动作与协议一致，命令编解码往返一致。
5. 接通真实环境与奖励：实现一次动作对应一次真实状态推进，保留前后基线；验收覆盖受伤、攻击、战斗完成、非战斗选择和整局终止。
6. 重建训练样本：保留来源、动作前后状态、确认结果与版本；按对局分割训练和验证，明确丢弃理由，避免相邻帧泄漏。
7. 再运行 SL 与小规模 RL：先验证训练入口、模型保存加载及 warm start 权重一致，再评估独立对局；报告运行数和失败原因，不把单场成功写成胜率提升。
